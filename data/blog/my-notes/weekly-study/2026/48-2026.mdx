### [我如何通过让 monorepo 对 agent 更友好，在一周内修复了 55 个 bug](https://www.devas.life/how-i-fixed-55-bugs-in-a-week-by-making-my-monorepo-more-agent-friendly/)

Takuya Matsuyama 在把 39 个仓库迁入 monorepo 后，继续重构应用代码，让编码代理复制正确模式而非坏模式：按功能重组目录、用 lint 强制模块边界，并在为严格 lint 修复补测试的过程中发现并修复约 55 个由他手工编写的 bug。文章的核心结论是代码库本身就是代理的记忆，纠正代理应落成确定性检查，而不是不断追加规则。

- 🧠 **代码库即记忆**：Lauren Tan 的演讲指出代码库是代理最大的输入之一，已有坏模式会被下一个代理当成惯例复制；因此每次纠正代理时，应优先转成 lint 等确定性检查，而不是继续往规则文件或 `AGENTS.md` 里加说明。
- 🧩 **按功能分组**：目录结构被视为上下文，代码从按类型分组改为按功能和层分组，避免 `utils`、`modules` 这类模糊分类；桌面端形成 `renderer/features` 下 15 个功能目录，每个功能只通过 `index.ts` 对外暴露，组件、hooks、actions、reducer、命令处理器和测试放在一起。
- 🛡️ **强制模块边界**：主进程和渲染进程不能再互相导入，否则 lint 报错；每个 IPC channel 都基于共享契约做类型约束，配置文件只允许主进程写入；移动端和 Web 编辑器也采用同一结构，减少跨边界导入和审查时到处查找。
- ⚙️ **严格 lint 拦截**：采用 Christoph Nakazawa 的 `@nkzw/oxlint-config`，其规则面向 anti-slop 且关注性能；初始在 2,422 个文件中报告 11,589 个问题，尚未全部完成，但仅 `rules-of-hooks` 就发现 18 个真实 bug，例如在提前 return 后或循环中调用 hooks。
- 🧪 **补测试找 bug**：为满足 `react-hooks/exhaustive-deps` 等规则，代理先在旧代码上补组件测试再修改；新增测试 uikit 385 个、mobile web editor 625 个、desktop 764 个、mobile 852 个，最终发现约 55 个 bug 且每个都有先失败的测试，例如编辑器搜索栏每次 effect 都订阅却从不取消订阅，导致“查找下一个”跳过多个匹配；移动端还有 13 个 bug 已被测试固定、等待修复。
- 🐛 **自动修复风险**：自动 fixer 并不总是安全：`catch-error-name` 把 `{ cause }` 改名为 `{ error }`，`prefer-node-protocol` 会破坏 React Native 的 `crypto` alias，`no-var` 会改写 `.d.ts` 文件里的 `declare var`。
- 🔄 **大规模迁移冲突**：目录移动后把 `main` 合并进 lint 分支产生了 145 个冲突；移动端还因从功能 `index.ts` 导出 Redux state 而让 Redux roots 反向加载组件，启动时新增 10 个 require cycle，后来通过每个功能增加第二个公共文件 `state.ts` 解决。
- ⚠️ **验证仍滞后**：迁移后尚未生成打包的桌面构建，CI 还没运行移动后的测试，Windows、Linux 和账号流程也仍未检查；作者下一步希望增加更多运行时验证。
- 💡 **工程方式转变**：作者意识到自己过去也像代理一样盲目沿用 Atom 的目录和编码模式，直到应用变大后旧模式不再适用；新的工程工作是从手工改代码转向通过工具和设计建立与代理的高信任，并在给代理加规则前先怀疑代码库和 lint 规则本身。

### [让 Agent 先问清楚、画出来、再证明：我的 Ryugi 工作流](https://innei.in/posts/tech/ryugi-workflow)

作者介绍了一套名为 Ryugi（流儀）的开源 artifact 工作流，用来把 coding agent 需要人拍板的事项从聊天框转移到可直接作答的页面：设计决策写成文档供逐题选择与评论，界面方案画在画板上供点选，完成后用验收页并排展示“批准的方案”和“运行截图/录屏”供逐组通过或驳回，页面上的选择会回到发起它的 agent 会话。文章以博客编辑器 haklex 去掉 Excalidraw 依赖、按原数据格式自研白板为例，记录了约半天内完成两轮开发、一次发版和三个下游项目适配的过程，作者在聊天框中的发言不到 20 条。

- 🧩 **Ryugi 的定位**：一套面向 coding agent 的 artifact 机制，把问题、方案和验收结果放到可交互页面上，而不是在聊天记录里来回追问。
- 📝 **设计文档会提问**：开场只有一句“去掉 excalidraw 依赖，根据它的数据结构来手搓一个 whiteboard”，agent 先读代码确认范围，再把问题嵌进设计文档，每题附推荐与理由；第一题是决定第一版规模的分岔题。
- ✅ **结论标明归属**：每轮回答后结论并入“已定”一节，并标明是作者定的还是 agent 代定的，方便快速识别哪些还需复核。
- 🧊 **冷读审稿代理**：设计稿交付前，由未参与讨论的审稿代理冷读，大部分问题由其自行处理，最后只剩两个交给作者决定。
- 🎨 **UI 改用画板**：因为界面“用文字讲不清楚”，改为每组并排几个方案、推荐项标红框并附便签理由；两轮共 5 组，作者都选了推荐项，选中的图链接进设计稿。
- 🧱 **批准后按任务推进**：设计稿被切成 19 个小任务，在单独分支上以“先写失败测试—再实现通过—提交”的节奏完成，自主决定的细节记入台账，对话被压缩时也照台账继续。
- 🔍 **独立审查与验收页**：完成后交给未参与开发的审查代理，问题逐个先补失败测试再修；随后在真实浏览器运行编辑器，截图录屏，与批准方案并排验收。
- 🔁 **验收可迭代**：作者逐组通过或驳回，曾在图上留言，agent 修改后重新截图放回同一位置；未能验证的部分单独列出，不混入“已完成”。
- 🖼️ **第二轮以参考图为标准**：作者贴出参考图询问原版 Excalidraw 能否实现，agent 逐元素对照能力缺口；作者限定“只做通用绘制能力”，再走设计文档、三轮问答、审稿、批准、实现、审查。
- 🚀 **发版与下游适配**：两轮通过后发新版本，再到三个使用该编辑器的项目逐个升级、跑测试并在浏览器确认白板显示正常，下游结果也放进验收页（浅色、暗色各一张）。
- 🔐 **仍需人工的环节**：整个过程中只有 npm 发布需要作者本人登录验证，agent 无法替代。
- 🧭 **边界与取舍**：流程不替作者做判断；开放题未填时 agent 会按自己理解补上并标出，验收页列出未验证项，是否补做由作者决定。
- 📦 **开源与安装**：Ryugi 已开源（github.com/Innei/ryugi），可在终端运行 `npx ryugi-artifacts install` 并选择所用 agent 安装；文中两份设计文档、画板和验收页均已公开。

### [智能体真的在终结 UI 吗？](https://posthog.com/blog/agents-killing-ui)

PostHog 的 Cleo Lant 撰文反驳「agent 正在杀死 UI」的流行说法：agent 确实成了软件的一类新用户，但界面并未消失，只是像当年的 API 和 GUI 一样，在产品之上又增加了一层。未来是混合（hybrid）而非无头（headless）——每个用户都会带着一个 agent 一起使用产品，因此构建者要为 agent 和人类分别设计入口，并把设计精力集中到审批、审查、撤销、可辨认性和编排这些真正需要人来判断的屏幕上。

- 🧩 **混合而非无头**：文章的核心论点是「我在用的一切都是用户界面」，agent 只是没在用你专门设计的那部分。headless 是叠加在产品构建之上的新一层，而非替代；产品构建者的工作因此翻倍：每个人类用户都会带来一个 agentic plus-one。
- 🔑 **首页不再是前门**：面向技术用户的上手流程越来越少从「get started」按钮开始，而是从终端或 AI 聊天窗口开始。用户可能经 Claude 或 ChatGPT 推荐（AEO）后由 agent 直接开通，永远看不到首页。但 agent 不一定会读安装文档，所以配置必须能被 agent 独立走完：容易找到、容易认证、一次调用完成而非十步。同时别忘了 agent 背后的人最终会打开产品，需要知道它做什么、下一步做什么。
- 🛠️ **两套入口的具体清单**：给 agent 的：能端到端完成的注册流程、在 Claude 和 Codex 等 agent 查找连接器的应用目录中有条目、可解析的文档（`llms.txt`、以纯 Markdown 提供的页面）、agent 即兴发挥时也安全的短时效 scoped token。给人的：若由 agent 代为设置，用户是从流程中段进入，要展示已完成与待完成；若自己点击进入，直接指向下一步。
- 💻 **文中实例**：`npx -y @posthog/wizard@latest` 一条命令创建账户、扫描代码库确定埋点位置并逐步在终端打日志，之后有人继续通过 MCP 以 headless 方式使用，也有人回到 Web 应用查看数据。Slack app 把消息提示变成 PR 草稿，但合并前仍要在 GitHub 看 diff（另一个 UI）。AgentMail 的文档教 agent 自助开通收件箱和密钥，但六位验证码仍需人接收并交付。
- 🔗 **AX 与 MCP**：computer-use 类 agent（如 Perplexity 的 Comet）会点击真实 DOM，但那是缓慢且「人形」的交互。agent 真正需要的是 AX（agent experience），当前标准是 Model Context Protocol：运行一个描述产品能力的服务端，agent 连接后直接与产品交互。要求是每个动作都有 agent 能执行的路径，以及人能核查它是否完成的路径。Vercel 的 MCP server 可查看部署、拉取运行时日志并触发部署，结果同步回仪表盘；PostHog 的 MCP server 让 agent 用你的凭证创建功能开关或实验，变更记入项目活动日志并附 `x-posthog-client` 头以区分 agent 与人的操作。
- 📈 **如何观测 agent**：agent 命中的是 API 而非前端，pageviews、autocapture 和 session replay 都捕不到它们的挫折信号；失败方式也不同：编造参数、认证墙、超时、幻觉出并不存在的工具，现有日志分类接不住。PostHog 因此做了 MCP Analytics，把每次工具调用（含 intent）转成事件；agent 去调用你并不存在的工具，等于机器人写的功能请求。上个月记录了近 1000 万次工具调用，来自 31 个 agent 客户端，背后是发短信告警、跑 A/B 测试、排查线上报错等真实工作。
- 🔍 **外部数据与配套设施**：Cloudflare Radar 6 月数据显示 HTML 流量中自动化请求首次超过人类，占 57.5% 对 42.5%，比其 CEO 的预测早约 18 个月。Temporal 把 agent 运行的每一步记录成可重放、可检查的持久事件历史，用来看循环卡在哪里或重复了什么。
- 🎨 **值得认真设计的六类屏幕**：审批（两秒内看懂自己在同意什么）、审查（给 diff 本身而非变更摘要）、撤销（agent 自主执行的动作旁要有回退）、可辨认（一屏内分辨同事与机器人的操作）、编排（五个 agent 是一屏看还是开五个对话）、打断（agent 运行中如何插手）。应降低会被 agent 取代的屏幕的优先级，把 MCP 当产品做；但 MCP 给的是触达而非质量，护城河可能是比对手更好用、更好看的 UI。Intercom 的 Fin Operator 把每项调整变成结构化提案（他们称之为 Operator 版的 pull request），由人审阅、编辑、批准后才生效；Anthropic 除了终端里的 Claude Code，还提供桌面应用、Web 应用、IDE 扩展和 Cowork。

### [压缩侧边栏的烦恼](https://blog.master.dev/the-compacting-sidebar-blues/)

文章讨论响应式应用侧边栏在视口高度不足时如何优雅降级：当导航项放不下时，隐藏文字标签只留图标，并重点分析“何时触发压缩”的几种方案及其陷阱，最终给出基于 CSS 样式查询与 `sibling-count()` 动态计算高度上限的解法。

- 📐 **问题场景**：屏幕太矮导致侧边栏导航项放不下，内部出现滚动条；对应用导航这种重要元素来说，内部滚动体验很糟。
- 🏷️ **降级方案**：压缩时移除文字标签、只留图标；作者认为这可作为第一个断点，并强调要用 `aria-label`，或让文字只是移出屏幕而非 `display: none`，以保持可访问性。
- 🔁 **“诅咒”方案**：用 `scroll-state(scrollable: y)` 在出现滚动条时压缩；但压缩后不再滚动，样式回退又变高，形成无限抖动循环。
- 🌀 **CSS 循环先例**：作者提到早期 CSS-Tricks 的“CSS-Jitter Man”演示——`:hover` 状态比原状态小，导致悬停时反复缩放。
- 🔢 **魔法数字断点**：直接写 `@container sidebar-height (height < 500px)` 隐藏标签；短期可用但脆弱，导航项数量、字体渲染、间距、图标尺寸变化都会让断点失准。
- ➗ **去魔法化计算**：用 `calc()` 累加侧边栏上下内边距、每个导航项的上下内边距、图标高度、图标与文字间距、文字高度，再乘以 `sibling-count()`；文字高度 14px 仍是唯一的魔法数字。
- 🚫 **自定义属性不能进查询**：`@container ... (height < var(--navItemHeight))` 无效，因为 `var()` 按元素解析，查询没有可解析的元素；作者推测这也是为了避免查询层面的无限循环，`@custom-media` 也帮不上忙。
- ✨ **样式查询解法**：注册 `@property --sidebar-h` 与 `--limit`，在 `.sidebar-inside` 上设 `--sidebar-h: 100cqh`，在每个 `.nav-item` 上计算 `--limit`，再用 `@container nav-item style(--sidebar-h < --limit)` 隐藏标签；由于 `--limit` 由不变常量算出，不会触发无限循环。
- ⚠️ **计算注意事项**：插入 `<hr />` 等额外子元素会打乱 `sibling-count()` 的计算；文字高度测量本身仍是棘手领域。
- 🌐 **浏览器支持**：Chrome 142+ 与 Firefox 154+ 可用；Safari 尚不支持样式查询中的范围语法，会保留标签，但不至于灾难。

### [button-sounds/docs/react.md（位于 main 分支） · joshwcomeau/button-sounds · GitHub](https://github.com/joshwcomeau/button-sounds/blob/main/docs/react.md)

button-sounds 的 React 文档围绕两个自定义 Hook 展开：高层 `useButtonSounds` 负责把元素 ref 与声音名绑定，在点击和释放时自动播放随机样本并预加载资源；低层 `useImperativeButtonSounds` 暴露 `press`、`release` 供调用方手动控制。文档同时说明音量、音高变化、lofi 位深/降采样参数，低层 API 下的嵌套 `pointerUp` 监听方案，以及音频文件默认走 JSDelivr CDN 或改为自托管的做法。

- 🧩 **高层 Hook**：`useButtonSounds` 接收元素 ref、声音名和可选参数；内部为每次 click 和 release 触发所选声音的随机样本，并预加载指定声音，声音名列表见 Sound Playground。
- ⚙️ **播放参数**：`volume` 默认 0.5，范围 0 到 1；`pitchVariation` 默认 0，按 +/- 调整 `playbackRate`，如 0.1 对应 0.9 到 1.1，也可传元组如 `[0.8, 1.5]` 手动设定随机最小/最大播放速度。文档建议音量取 0.25 到 0.5，音高变化少即是多，0.05 也能产生不错的变化，具体取决于声音。
- 🎨 **lofi 效果**：`lofi` 默认 false，启用后 `lofiOptions.bits` 默认 4，位深越低量化误差使声音更粗糙；`lofiOptions.downsample` 默认 0.25，降低采样率后声音更深更浑浊；`lofiOptions` 仅在 `lofi` 为 true 时生效。
- 🔄 **低层 Hook**：`useImperativeButtonSounds` 返回 `press` 和 `release`，由调用方决定何时触发；两者可选参数包括 `sampleIndex`（指定样本，省略则随机）、`volume`（默认 0.5）、`playbackRate`（默认 1）以及与高层 API 相同的 `lofi`/`lofiOptions`；低层 API 不提供 `pitchVariation`，而是每次调用直接指定实际 `playbackRate`。
- ⚠️ **嵌套事件**：低层 API 文档建议不要并列添加 `pointerDown`/`pointerUp`，而要在 `pointerDown` 处理器内嵌套 `pointerUp` 逻辑，并用 `window.addEventListener('pointerup', ..., { once: true })` 注册全局一次性监听；这样可避免在按钮上释放选中文本的鼠标时误播释放音，以及按下后移出按钮再释放时漏播释放音。
- 🌐 **自托管音频**：默认会从 JSDelivr CDN 下载 .mp3，例如 `https://cdn.jsdelivr.net/npm/button-sounds@0.0.0/assets/hi75-soft.mp3`；也可自行下载音频文件并把库指向自有副本，详见“Self-hosting the audio files”文档。
- 💡 **使用范围**：技术上 `useButtonSounds` 可作用于任意有效 DOM 节点，但文档强烈建议仅用于 `<button>`、`<a>`、`<input>` 等交互元素。

### [agent-device：面向智能体的开源设备层](https://agent-device.dev/)

agent-device 以开源设备层的形式把编码代理接入真实应用运行环境，让代理在本地或云端的真机、模拟器和设备上控制移动、Web、TV 与桌面应用，并把截图、视频、日志和可回放脚本作为验证证据带到评审与 CI 中。它补上了代理写完代码后无法亲自到设备上验证的环节，同时通过 `.ad` 脚本、JUnit 报告、MCP/Node.js API 和托管设备接入，把代理自测、回归回放、性能剖析与多人多代理协作串成一条可执行链路。

- 🚀 **开源发布**：agent-device 是面向编码代理的开源设备层，让代理在本地或云端的真机、模拟器上控制移动、Web、TV 和桌面应用；支持 iOS、Android、HarmonyOS、tvOS、Android TV、Fire TV、Vega OS、macOS、Linux、Web、React Native、Expo、Flutter，安装命令为 `npm i -g agent-device`，页面显示 npm 3M+/mo、GitHub 5.5K。

### [🗺️ Query v6 路线图 · TanStack/query · 讨论 #12669 · GitHub](https://github.com/TanStack/query/discussions/12669)

TanStack Query 维护者 TkDodo 宣布启动 v6，主线不是大规模重写公开 API，而是借大版本清理内部实现、更新工具链与支持范围，并分项收集反馈；ESM-only、React 19 最低版本、微任务调度、必填 queryFn、哈希与相等性、streamedQuery 稳定化等已实现，gcTime 语义、queryOptions 下沉 core 仍在计划中，enabled 移除和服务端 gcTime 等仍在讨论，官方不承诺时间表。

- 🚀 **版本定位**：v6 已开工，但官方强调大版本用于破坏而非加功能，目前不计划大规模改写使用方式；开发分支为 `query-v6`，不做时间承诺，并会关闭未经沟通的全自动 PR。
- 📦 **仅发布 ESM**：放弃 CJS 和面向旧 webpack4 的 legacy 构建，简化构建并推动生态转向 ESM；状态为已实现。
- ⚡ **React 最低 19**：React 适配器最低要求提高到 v19，内部在 `useSuspenseQuery` 的 Suspense 集成中使用 `use()`，替代已弃用的 throw promise；状态为已实现。
- 🔄 **默认调度改微任务**：默认调度器从 `setTimeout(0)` 切换为 microtask，以获得更好的批处理效果，并缓解 await 失效后 setState 渲染旧 query 数据的问题；状态为已实现。
- 🛠️ **移除 v5 弃用 API**：删除 v5 标记弃用的接口，包括 query-core 的 `context.direction`、`isInitialLoading`、`queryClient.fetch/prefetch/ensure(Infinite)Query(Data)`、`queryObserver.getOptimisticResult`，solid-query 的 suspense option，sync-storage-persister，vue-query 的 Vue 2 via vue-demi，以及 devtools 的 styleNonce；状态为已实现。
- 🎯 **queryFn 必填**：`useQuery` 及框架适配器中的 `queryFn` 改为必填；需要全局默认函数时应显式传入导出的 `defaultQueryFn`，避免隐式依赖前一个组件渲染时提供的 queryFn；状态为已实现。
- 🧩 **全局 hashFn 与 equalityFn**：用 QueryClient/QueryCache 级别的全局 `hashFn` 取代 queryOptions 里的 `queryKeyHashFn`，解决同一 QueryKey 多哈希函数导致精确查找不一致；新增 `equalityFn` 可传入 `replaceEqualDeep`，为 Date 等非 JSON 类型自定义结构共享；状态为已实现。
- 🧪 **streamedQuery 稳定化**：`experimental_streamedQuery` 提升为稳定 API，结束实验状态；状态为已实现。
- 🌐 **提高浏览器基线**：最低支持 Chrome/Edge 119、Firefox 121、Safari/iOS 17.4、Opera 105，以便使用 `promise.withResolvers` 等现代浏览器 API；状态为已实现。
- ⚙️ **重试加入 jitter**：默认指数退避重试延迟加入 jitter，避免 thundering herd；因属于行为破坏性变更，只在 v6 发布；状态为已实现。
- 🧭 **gcTime 改为 last wins**：计划把同一 query 多次设置 `gcTime` 的规则从当前最高值胜出改为最后一次设置胜出，使选项覆盖更确定；状态为计划中。
- ⚠️ **enabled 拟由 skipToken 取代**：讨论移除 `enabled`、改用 `skipToken`；难点是无法复刻永久禁用后按需 `refetch()` 的模式，维护者希望先确认实际使用情况，尚未决定。
- 🎨 **queryOptions 下沉 core**：计划把 `queryOptions` 移入 `query-core`，各框架适配器只再导出或覆盖自身实现；此前受类型问题阻碍，现由协作者推进，并归入 v6 以控风险；状态为计划中。
- 🔍 **服务端 gcTime 待改进**：讨论服务端 `gcTime` 行为：默认是 `Infinity`，但直接传给 `useQuery` 的值仍会在服务端生效，已有文档提示但投诉增加；同时需保留服务端 GC 以支持长生命周期 QueryClient，尚未定案。
- 🛡️ **HydrationBoundary 清理**：移除 HydrationBoundary 中受类型保护的防御检查；但 pages router 使用 `pageProps.dehydratedState` 时用户可能需要额外守卫，维护者表示必要时可回退；状态为已实现。

### [同步的力量 | Seth's Blog](https://seths.blog/2026/11/the-power-of-sync-2/)

Seth Godin 在《The power of sync》中指出，同步工作按共享时间表实时发生，异步工作则按各自的节奏推进；两者各有成本与收益，但几乎没有人认真核算同步的代价。文章用电话与短信、电视与流媒体、写剧本与拍电影、会议与备忘录等对比，说明同步能放大能量、提升特定流程效率并提供控制手段，却也可能让能量向下螺旋、消耗韧性，并让工作安排偏离工作者与市场的实际需求。作者进一步把截止日期、会议召集权、Slack 造成的「假异步」、媒体公司的模式翻转、远程办公困境和 AI 作为天然异步参与者等现象串联起来，主张只在同步能带来明确优势时才采用同步，并重点关注两种模式切换的交接点。

- 🧩 **同步与异步之分**：同步工作是按共享时间表实时一起推进，异步工作是按自己的时间表推进。电话是同步，短信是异步；网络电视是同步，YouTube 和 Netflix 是异步；写剧本是异步，拍电影和首映是同步；员工会议是同步，备忘录是异步；民航是同步，私人飞机是异步。每种方式都各有成本和优势。
- ⚡ **同步的三个优势**：一是能量可倍增，有人贡献时其他人会努力追赶或超越，从而形成放大整体投入的环境；二是在特定流程上更高效，例如甜甜圈必须在炸好后立刻上糖霜，且贡献者能实时看到接收方的反应并据此调整；三是提供指挥、控制与某种形式的检查。
- ⚠️ **同步的代价与风险**：能量也可能向下螺旋，成员情绪脱节或身体缺席会拖累整个互动；缺少余量与韧性，在片场常出现大量等待；很难匹配工作者和市场的真实需求；也让人难以对工作细节与项目走向保持清晰、有意图的安排。
- 🔄 **交接点是杠杆所在**：现代世界的杠杆与摩擦大多发生在工作模式切换的地方。截止日期就是一个典型例子：它是强加在异步工作之上的同步点。
- 🔑 **谁掌握时钟就是谁掌握权力**：同步不只是排期选择，也是权力的展示：召集会议的人已经决定了如何占用所有人的时间。老板叫开会，员工写备忘录。异步把权力从协调者转移到创造者。
- 🐛 **假异步**：异步会随着时间逐渐向同步靠拢。Slack 消息、短信和邮件之所以成功，是因为它们原本是异步的，但如今却制造出实时回复的预期；结果是人们承受了同步的打断，却没有得到同步带来的能量。
- 📊 **媒体公司的模式翻转**：偏爱既有同步或异步模式的媒体公司，常在消费方式变化时陷入困境。Amazon 和 Netflix 之所以存在，正是因为它们那些同步模式的前辈没能处理好与客户的异步关系；而 Netflix 转向一次放出全季虽筑起护城河，却削弱了口碑，Nathan Fielder 的电影在首周被讨论的热度远高于其流媒体剧集。
- 🏢 **远程办公的启示**：六年前被迫居家办公时，一些组织拥抱了异步带来的好处，许多管理者却因无法实时看到员工而不知所措。根源在于员工被灌输「有人看着才算工作」的观念；而另一些人像高效写作者那样，在没有实时同步干扰的情况下真正完成了工作。
- 🔮 **AI 目前是异步的**：agent 永远不需要开会，还能在凌晨 3 点工作，于是人类反而成了同步流程的瓶颈。随着其能力增强，可以预期 AI 将成为大多数同步事件的参与者。
- 🔗 **信任在同步中建立、在异步中消耗**：异步在已经互相了解的人之间效果更好。新团队、新员工和新客户关系初期可能需要同步；替代方案是构建天然异步的系统，让新参与者通过在线声誉系统和有设计的在线社区以新的方式赢得信任。
- 📝 **三条行动原则**：不要采用同步，除非它能比异步带来有价值的优势，并说明理由、为之辩护；做异步工作时要匹配自己的内在节律，以不同于分配顺序的方式完成更多事情；留意同步与异步之间的切换，机会与陷阱都在那里。组织还应更留意同步的成本，创作者则应为不同种类的工作合理定价，这也是请 Bob Dylan 在生日派对上唱歌要价一百万美元的原因。
