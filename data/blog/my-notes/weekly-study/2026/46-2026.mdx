## 技术

### [从零重建全球公共广场](https://blog.x.com/en/engineering/rebuilding-the-global-town-square-from-scratch)

X 首席工程师 Yagiz Nizipli 撰文说明为何重写 X.com 的 Web 应用：旧架构由 rweb、rweb SSR、Jetfuel SSR 三套服务器分别服务普通用户、搜索引擎爬虫和链接预览机器人，导致同一个 URL 有三条构建路径、SEO 修复容易漏改、未登录用户反而拿到最慢的客户端渲染路径。团队选择新建一个应用、由同一台服务器按访问者类型分别渲染，并让旧系统继续服务、按国家逐步迁移流量。文中还介绍了新技术的组成与保留下来的旧系统能力；但原文在介绍 Rust 卡片图服务处被截断，尚未包含承诺的性能优化细节。

- 🚀 **性能对比**：在慢速连接下，旧 Web 应用要盯着 X 标志超过 22 秒才出现第一条帖子；新版为 2.7（原文未标单位，按上下文推断为秒）。
- 🖥️ **三服务器合一**：新的 Web 应用把原先分别服务用户、搜索爬虫和链接预览的三台服务器合并为一台，目前已承载未登录的 X.com 和搜索引擎抓取页面，登录版正在迁移。
- 👥 **团队与周期**：五名工程师借助 AI 编码代理，用不到六个月做出新应用第一版；随着登录页面迁移，团队规模扩大，自 9 月底以来已有 20 多人向该应用提交代码。
- 🌍 **分阶段上线**：先在 lite.x.com 上由员工和测试人员验证，再按国家逐个迁移登录用户；旧服务器会一直运行到所有人迁移完成。
- 🕰️ **历史沿革**：2017 年的 Twitter Lite 是面向慢速连接的 PWA，采用“HTML 应用外壳 + 浏览器直接请求 API”模式；2019 年同一代码库成为桌面版 Twitter.com，即 rweb，其客户端渲染链路正是慢速连接问题的根源。
- ⚠️ **三类访问者的需求冲突**：普通用户想要尽快看到资料和最新帖子；Googlebot 和 Bingbot 需要完整 HTML、结构化数据、各语言版本链接及正确状态码；iMessage、Slack、Discord 等预览机器人只需要标题、描述和图片。
- 🧩 **数据是图结构**：帖子有作者，作者有资料，帖子还可能引用其他帖子及其媒体，浏览器往往要下载并执行代码后才发现这张图；在慢速网络上，每一步都是额外往返。
- 🔧 **旧架构的三个问题**：三台服务器逐渐各自偏离，SEO 修复常常只落在其中一台；未登录用户拿到的是最慢的应用外壳路径，而爬虫拿到现成 HTML，机器人反而得到更好的待遇；技术栈新旧混杂（Redux + Relay、React Native for Web 样式组件、Flow、现代与旧版双 bundle），团队称为“千刀万剐”。
- 🛠️ **三种方案的取舍**：继续改进 rweb 会保留三台服务器，若要给未登录用户服务端渲染，还得再造第四条渲染路径；只换工具链（Vite、TypeScript、Fastify）几乎改动每个文件，却留下原有架构；最终选择新建单服务器应用并逐步迁流。
- 🧱 **为“不要重写”质疑的回应**：rweb 全程继续发布，流量逐步迁移，并用旧服务器作为规格来测试新应用；借助代理承担大量实现，重写只用了数月，旧产品来不及拉开差距。
- 💾 **有意保留的资产**：相同 URL 及重定向与别名、rweb SSR 的 URL 清理规则、Jetfuel SSR 的结构化数据、语言替代链接与 404 页面、逐像素重绘的链接预览卡片图，以及“一套响应式代码适配所有设备”的产品模型。
- ⚙️ **新技术栈**：Vite（Rolldown 构建、本地开发）、React（流式服务端渲染 + Suspense）、Fastify（统一请求处理）、Platformatic Watt（Node.js v26 上多工作线程，超限工作线程会被替换）、Relay + GraphQL、XDS 组件库（40 多个组件，基于 Base UI 和 Tailwind CSS）、TypeScript 与 Tailwind，类型检查用 Rust 版编译器 tsrs；登录与未登录用户有独立客户端入口。
- 📄 **按访问者类型分别渲染**：真人获得流式 HTML，页面外壳先发、数据到达即流入，GraphQL 响应随页面只传一次供浏览器复用；经边缘节点验证 IP 的搜索爬虫获得一次性发送的完整文档，所有 Suspense 边界已解析。
- 🔐 **为何验证 IP 而非 User-Agent**：检查 UA 会把 Lighthouse 等性能工具也当成爬虫一起缓冲，还会让任何人仅改请求头就要求更昂贵的渲染路径；用验证过的 IP 可让 Lighthouse 测到的就是真人拿到的流式页面。
- 🤖 **预览机器人获得最小响应**：服务器只执行路由数据加载和 head 标签，跳过正文渲染，也跳过只有正文需要的时间线和会话请求；未经边缘验证的爬虫（包括自称搜索引擎的请求）得到的与未登录访客完全一致。
- 📦 **爬虫文档不 hydrate**：不含客户端 bundle、路由状态或需要 JS 替换的占位符；Googlebot 只读响应前 2 MB，而长推文串的 HTML 可能超出，如何压回限制留待性能章节（原文此处截断）。
- 🦀 **卡片图改用 Rust**：链接预览 PNG 按需绘制，原 JavaScript 服务只能靠多实例利用多核且不共享内存，事故期间响应曾需约两分钟；新 Rust 服务的内容在文档中未展开。

### [让 TanStack Query 在各标签页间保持最新 - DEV Community](https://dev.to/idanshalem/keeping-tanstack-query-fresh-across-tabs-2k80)

TanStack Query 默认每个标签页各自维护缓存，因此一个标签页中的变更不会自动同步到其他标签页；文章提出用 BroadcastChannel 广播“某个 queryKey 已失效”，让各标签页自行重新请求数据，而不是直接广播新数据。该模式也可用于跨标签页登出，但服务端会话失效仍是安全边界，广播只改善 UI 同步体验。

- 📌 核心问题：在标签页 A 修改变更后，标签页 B 的 TanStack Query 缓存仍是旧数据，除非重新聚焦窗口或触发重新请求。
- 📡 解决思路：通过 `BroadcastChannel` 发送“这个 queryKey 已失效”的事实，而不是发送新数据本身。
- 🔐 为什么不广播数据：每个标签页已有自己的鉴权、筛选条件、错误处理和请求逻辑，只发失效信号更简单、更安全。
- 🧩 实现方式：在 `QueryClientProvider` 内挂载一次 `CrossTabInvalidation`，监听 `invalidate` 消息并调用 `queryClient.invalidateQueries({ queryKey })`。
- 🔁 发送方行为：执行 mutation 的标签页先在本地失效查询，再广播给其他标签页；浏览器不会把消息回传给发送它的 `BroadcastChannel`。
- ⚠️ 刷新细节：只有活跃查询会立即重新请求；其他匹配查询只会被标记为过期，带 `enabled: false` 的查询不会自动重新请求。
- 🚫 无消息重放：后打开的标签页收不到之前的广播，只能依赖自身请求；若持久化查询缓存，数据新鲜度取决于 `staleTime` 和 `gcTime`。
- 🧱 查询键要求：queryKey 必须可克隆，只应使用字符串、数字、普通数组和对象，不能包含函数。
- 🚪 跨标签页登出：同样可广播登出事件，但应先结束服务端会话，再广播，再清理当前标签页；服务端拒绝后续请求才是真正的安全保护。
- 🛡️ 错过登出消息：关闭或冻结的标签页可能收不到广播，敏感页面应在重新回到标签页时显式校验会话，并在校验期间隐藏私有内容。
- 📚 文章还提供两个文档配方：TanStack Query 跨标签页失效，以及跨标签页登出。

### [OhMyGame](https://github.com/WhiteTowerAI/ohmygame/blob/main/README.zh-CN.md)

OhMyGame 是一个开源的一人游戏工作室应用，把游戏设计文档、2D/3D 美术、视频、音频、代码、试玩和发布整合在同一块画布中，由 AI Agent 驱动，并使用用户自己的模型密钥。文档称其目前处于 Beta 阶段（beta 5），项目采用 Apache-2.0 许可证。

- 🚧 **Beta 状态**：OhMyGame 目前处于 Beta 阶段；2026-10 发布 beta 5，新增互动故事支持。
- 🧩 **产品定位**：把原本分散在设计文档、2D 美术、3D 模型、视频、代码和发布等五六个工具中的工作，收进一个应用；用户描述游戏后，Agent 负责设计、制作素材、搭建、试玩并发布为可分享链接。
- 🖼️ **核心画布理念**：每个项目有设计空间，主设计文档与图片、视频、3D 模型、音频并排；节点可互相引用，生成结果进入共享素材库（Asset Library）。
- 🤖 **Agent 自动工作**：Agent 像用户一样操作画布，起草文档、生成素材、编写代码，在实时预览中运行游戏并亲自试玩 Canvas 和 WebGL 游戏；发现问题会尝试修复后再玩。
- 🎬 **互动故事**：适合视觉小说、互动电影和剧情游戏；每个画面是自由网页，可放视频、对白、选择甚至小游戏，不受固定节点类型限制。
- 🧑‍💻 **自带 Agent**：可选择 Claude Code、Codex 或 OpenCode 运行对话，使用其自身登录，同时仍可使用画布、媒体生成、试玩、插件和撤销，对话记录保留在 OhMyGame。
- 🔌 **MCP 接入**：在“设置 → MCP 服务”中把 OhMyGame 加入 Claude Code 或 Codex，可获得媒体生成、画布、试玩能力和工作流 Skill；DeepSeek Harness 等 MCP 客户端可添加 `ohmygame-studio` 命令。
- 🧩 **插件生态**：引擎侧支持 Godot、Unity、Unreal Engine、Cocos Creator；平台侧支持 TapTap Maker、微信小游戏、抖音小游戏；素材侧支持 Blender、Aseprite、Tiled；也可用插件构建器自建插件，引擎插件需先安装对应引擎。
- 🎮 **网页游戏**：文档称最推荐的起点，使用 Three.js、React Three Fiber 或 Phaser；适配任意窗口尺寸、支持触屏，发布为可分享链接，项目本身是普通 Web 项目。
- 🎲 **General Game**：不预设引擎和技术栈，可从想法开始、导入任意引擎项目或制作工具与内容；网页产物可预览、试玩和发布，原生游戏使用各引擎工具。
- 🔗 **发布与社区**：登录后可构建游戏并生成浏览器可玩链接，重新发布更新同一链接；社区可按最新、最多浏览、最多点赞排序，查看创作者主页并点赞。
- 💰 **变现方式**：微信/抖音小游戏靠广告和内购；TapTap 靠下载和内购；Steam 等商店买断，经 Godot 或 Unity 插件导出；itch.io、Poki、CrazyGames 可直接上传网页构建产物。文档明确称不从游戏收入中抽成。
- 🧠 **任意模型、自带密钥**：通过 Pi 接入 40 多家服务商，包括 Anthropic、OpenAI、Google、DeepSeek、通义千问、Kimi、智谱 GLM、MiniMax、xAI、Mistral、Groq、OpenRouter、Amazon Bedrock、Vercel AI Gateway；可登录 ChatGPT Plus/Pro、GitHub Copilot 或粘贴 API 密钥，无按次计费点数。
- 🎨 **媒体模型接入**：图片、视频、3D 和音频生成可通过 OpenAI、Codex、OpenRouter、火山方舟 / BytePlus ModelArk、MiniMax、Meshy、Tripo、Hyper3D、豆包语音 / Seed Audio 接入；支持自定义服务商和模型别名。
- 🔐 **密钥安全**：密钥只保存在本地守护进程，不会进入 Agent 的工作区、游戏或渲染进程。
- ⚙️ **实现原理**：运行带图形界面的完整 Pi Agent，具备完整工具集和持久化会话；每个工作区都是文件（Web 项目、Markdown 设计文档、JSON 节点模型、磁盘节点图），并附 `AGENTS.md` 和 JSON Schema；试玩（`game_use`）、生成媒体、检查故事节点均为普通 Pi 工具调用。
- 💻 **下载与首次运行**：Releases 提供 macOS（Apple 芯片）和 Windows（x64）版本，Windows 版暂无代码签名，可能触发 SmartScreen；应用不内置模型，首次启动需选择语言、连接模型（可跳过）、选择起点（描述游戏、空白项目或导入文件夹）。网页搜索无需配置；本地做游戏不需要账号，仅发布需登录。
- 📋 **能力与服务商对应**：设计文档、代码、试玩需任意语言模型；图片需 Codex CLI、OpenAI、OpenRouter 或火山方舟 / BytePlus ModelArk；视频需 OpenRouter、火山方舟 / BytePlus ModelArk 或 MiniMax；3D 需 Meshy、Tripo 或 Hyper3D；配音、音效、音乐需豆包语音和 Seed Audio。文档提醒 ChatGPT 登录不包含 OpenAI 图片 API，需另加 API 密钥。
- 🛠️ **源码运行**：需 Bun 1.4.2+、守护进程 Node.js 22.19+；克隆 `main` 分支后执行 `bun install --frozen-lockfile`，再运行 `bun run dev` 或 `bun run dev:desktop`；参与开发应从 `dev` 分支开始。
- 🕵️ **隐私**：项目和密钥留在本地，提示词与生成请求直接发送给所选模型服务商；发布需 OhMyGame 账号且只上传静态构建产物；正式版会检查更新并发送使用数据和崩溃报告，可在设置中关闭；源码构建版本不发送遥测；桌面应用本地保留脱敏日志，仅在导出诊断信息并分享时离开电脑。
- 🗺️ **路线图**：正在做通俗易懂的试玩报告、从社区 Remix 游戏，以及 Intel Mac / Linux 版本；可在 Issues 投票，`help wanted` 标签下可参与。

### [Text.js | 控制台框架](https://textjs.org/)

Text.js 是一个把全栈 React 应用直接渲染到浏览器控制台 `console.log` 中的框架，提供 React 组件、App Router 路由、服务端渲染、终端与 AI 代理运行能力，以及完整的开发工具链，让控制台变成可交互的应用界面。

- 🚀 通过 `bunx create-text-app` 快速创建项目，使用 `AsciiFont`、`Box`、`Text`、`useInput` 等组件构建控制台界面。
- 🧭 采用 App Router：`app/` 中的文件夹自动成为路由和布局，支持前进、后退与深链接，并适配 DevTools 面板尺寸。
- ⌨️ 统一处理键盘输入、粘贴和 IME 组合输入，通过隐藏的 `<textarea>` 将事件传递给应用。
- 🧱 提供布局、数据展示、图表、表单控件和键盘交互组件，如 Grid、Table、LineChart、Input、Dialog、CommandPalette 等。
- ⚙️ 渲染管线包括 React 自定义 reconciler、Yoga 布局、CellBuffer 绘制、脏行检测、RLE 编码和 `console.log` 输出。
- 📉 只有发生变化的帧才会产生一次 `console.log`；未变化帧为 0 次调用，并采用追加帧而非清空控制台，减少闪烁。
- ⚡ 性能示例：3,200 个单元格编码为 149 个 `%c` span；单行编辑约 0.011ms，完整重绘约 0.163ms，空闲帧 0 次调用。
- 🖥️ 支持 `runtime = "server"` 服务端渲染，浏览器只加载约 21kB gzip 的帧播放器，并通过 SSE 接收行增量。
- 🧩 支持 Partial Prerendering、中间件、缓存与 stale-while-revalidate，以及 static、bun、vercel、cloudflare 等部署适配器。
- 💻 同一套应用还可在终端中以真彩色 ANSI 运行，或通过 MCP 供编码代理导航路由、按键并读取文本帧。
- 🛠️ 配套 DevTools 扩展、VS Code 预览、ESLint 插件、测试工具、错误码文档和 `window.text` 控制台 REPL。
- 🌍 支持 Unicode 双向文本算法与 FIGlet 字体解析，并提供 10 章、约 65 分钟的控制台部署仪表盘课程。

### [GitHub - paulirish/chrome-capture：从 Chrome 以 60-120fps / 2160p 捕获标签页视频/音频 · GitHub](https://github.com/paulirish/chrome-capture)

chrome-capture 是一个基于 Chrome 新版原生录屏能力的开源工具，可直接把标签页以 60–120fps、最高 2160p 录制成 AV1 编码的 MP4，并支持标签页音频，无需 ffmpeg。它封装了 Chrome 153+ 的 `Page.startScreenRecording`，相比旧方案在速度、文件体积和录制体验上都有明显提升。

- 🎥 支持 60–120fps、最高 2160p 的标签页视频与音频录制，输出 AV1 `.mp4`，无需 ffmpeg。
- ⚡ 基于 Chrome 153+ 原生 `Page.startScreenRecording`，视频帧从合成器经共享内存直达独立编码器，边录边写入 MP4。
- ⏹️ 停止录制几乎即时完成，无需像 ffmpeg 方案那样等待数秒收尾；可随时开始/停止，适合只录关键交互。
- 🧩 Puppeteer v25.10+ 已提供实验性 `page.record()` 并弃用 `page.screencast()`；Playwright 仍使用旧 `Page.startScreencast`，预计后续跟进。
- 💻 CLI 用法简单：`npx chrome-capture <url> <output.mp4> <duration>`；默认录制音频，≤60fps 时无头运行，macOS 上 >60fps 自动切换有头模式以利用 ProMotion 120Hz。
- 🛠️ `startRecording()` 支持 Playwright Page、Puppeteer Page 或原始 CDP 会话，默认 60fps，可配置输出路径、分辨率、录制区域和音频。
- 🧪 提供 `@playwright/test` fixture，可自动录制每个测试并附加 MP4 到报告。
- 🖱️ 可通过 Playwright `showActions()` 或自定义 DOM 覆盖层把光标、点击徽章等录进视频。
- 📊 M4 Max 基准测试中，6.4 秒 UI 回放：旧方案 25fps、总耗时 21s、停止耗时 3800ms、WebSocket 流量 10.5MB；新方案 60fps、总耗时 11s、停止耗时 17ms、流量 450KB。
- 📦 新方案文件更小、画质略优：示例中最终文件 330KB vs 480KB，PSNR 34dB vs 32dB，并支持可选音频。
- 🎚️ 暂无码率/CRF 参数；Chrome 使用 libaom AV1 实时 1-pass VBR，码率随像素率线性增长，如 720p30 约 2Mbps、1080p60 约 9Mbps、2160p120 约 72Mbps。
- 🚀 压力测试显示：Mac 无头可达 2160p60；120Hz ProMotion 有头可达 1080p120 和 2160p120；无 GPU 的 Linux CI 可达 1080p60/1440p60，解除 vsync 限制可到 1080p75–83fps。
- ⚠️ macOS GPU 加速环境不要同时启用 `--disable-frame-rate-limit --disable-gpu-vsync`，否则 rAF 过快会拖垮采集。

### [程序员的悖论：小事](https://theprogrammersparadox.blogspot.com/2026/10/little-things.html)

文章总结了作者多年编程中形成的若干“小习惯”，核心是提前准备、消除未知、用函数表达意图、保持命名与代码清晰，并通过抽象、重构和对细节的重视来提高开发效率与代码可靠性。

- 🛠️ 编码前尽量做好准备工作：环境、磁盘、外设、家具，以及日志、错误处理、配置、密钥和安全基础都应先就绪，减少后续干扰。
- ❓ 不要留下疑问：如果不知道“做什么”或“为什么做”，现在就查清楚，不假设、不忽略、不拖延。
- 🧩 多用函数给代码块命名：函数名应简洁明确，通常是一个动词作用于输入名词，避免晦涩命名；函数也可替代注释，便于审查、分解和重构。
- 🧱 拆分前置条件与核心逻辑：把断言、错误处理、小计算等放在函数开头，让核心逻辑不被干扰；每个后续要用的数据都放进独立变量，相关逻辑聚在一起。
- 🔁 不要害怕大幅重构：发现方向错误或逻辑颠倒时立即修正，不要因为已投入时间而继续硬撑，否则会变成时间黑洞。
- 👀 重视可读性细节：代码要便于几个月后自己回看，也能让隐藏问题更容易暴露。
- 🏷️ 对命名保持敬畏：认真找到技术层面和业务领域中真正准确的名称；错误命名会吸引 bug，甚至长期传播造成困扰。
- ➰ 谨慎对待循环：能不用就不用，循环要拆出来并能证明其必要性；循环往往是性能问题的源头。
- 📈 不要硬磨大量样板代码：如果感觉要用 50 小时重复劳动，就退一步寻找更好的抽象或泛化方式。
- 🧠 不要耍小聪明，要聪明而清晰：显式写清楚通常更安全，语法糖可能变成以后会踩到的地雷。
- 🎯 代码不是系统本身，但它是控制系统行为的关键：代码规模越大，风格、格式、组织、一致性和细节越重要；要追求精确，以便在关键时刻可靠地完善代码。

### [面向渐进式自主的委托设计](https://www.telerik.com/blogs/design-delegation-progressive-autonomy)

AI 智能体的自主权不应是一次性开启的开关，而应像培养新人一样逐步授予：先判断任务是否适合交给智能体，再通过小步协作、过程观察和有限派出建立信任；自主权应像旋钮一样可调，并始终保留监督、干预与回退机制。

- 🎚️ **自主权是渐进旋钮，不是二元开关**：根据实际表现逐步扩大授权，避免第一天就完全放手，也避免永久人工审核。
- 🧑‍⚖️ **先判断再委托**：让用户决定哪些工作值得自动化、哪些任务适合交给智能体，而不是由软件强行接管现有流程。
- 🧪 **用小型、可见的步骤测试**：让智能体在关键决策点请求确认，支持人机协作，而不是提交后长时间等待一个难以检查的结果。
- 👀 **展示过程而不仅是结果**：公开智能体的推理、意图和中间状态，让用户能检查进度、及时停止并降低风险。
- 🔁 **为失败轮次设计**：保留操作日志、可逆操作和手动路径，允许用户随时把自主权调低。
- 🛫 **逐步“派出”智能体**：信任增加后，可延长自主运行间隔、减少接触点，但仍要允许用户陪伴、查看和介入。
- 🧑‍✈️ **自主不等于孤立**：像新人出差有人陪同一样，智能体执行任务时也应让用户能看到其工作位置并随时接管。
- 🧱 **产品设计应体现授权层级**：界面要反映用户授予的自主程度，显示智能体正在操作的范围，支持监督和回退。
- 💡 **结论**：用“判断、挑战、观察、派出”的模式设计智能体产品，让用户有时间逐步建立信任，并在信任不足时随时收回自主权。
