### [在删除你的 AGENTS.md 之前，请先阅读这篇文章——作者：Jina Yoon](https://newsletter.posthog.com/p/your-agentsmd-is-holding-you-back)

文章指出，上下文工程正从“不断补充信息”转向“主动做减法”，避免过多规则和提示反而拖累 AI 智能体。作者建议定期删除或重写 AGENTS.md / CLAUDE.md，并通过人工审查、评估测试和智能体反馈三种方式，让上下文保持精简、准确和可维护。

- 🧠 模型能力提升后，过去必需的上下文可能变成负担；Anthropic 曾移除 Claude Code 系统提示的 80%，Claude Code 创作者也建议每六个月删除 CLAUDE.md 以保持前沿。
- 🩺 先运行 `/doctor` 做基础健康检查：删除冗余提示、发现损坏配置、清理未使用插件、优化懒加载，并估算可节省的 token。
- 👀 `/doctor` 不能判断内容是否正确，仍需人工逐行检查 AGENTS.md；如果说不清某条规则能防止什么失败，就删除它。
- ⚠️ 文章举例：团队暂停 merge queue 后忘记更新 AGENTS.md，导致智能体在 21 小时内给出错误合并指令，说明上下文必须随外部状态同步维护。
- 🧪 把上下文当作代码来测试：每次智能体出错，就记录触发错误的提示到 `failures.md`，修改 AGENTS.md 后重跑这些提示作为回归测试。
- 🔁 PostHog 用约 40 个示例应用运行 Wizard，再由 `pr-evaluator` 评估生成的 PR，从中发现如“跳过安装 PostHog”等问题。
- 💬 直接让智能体反馈上下文缺口：在提示中询问哪些信息本可避免工具失败、错误编辑和无效轮次，并将反馈聚类、验证后用于改进上下文系统。

### [我如何使用 AI（2026 年 10 月）——本·斯托洛维茨](https://ben.stolovitz.com/posts/how-use-ai-oct-2026/)

作者在 2026 年 10 月回顾过去一年使用 AI 的变化：他从微软 Windows AI 团队工程师转为 Salesforce AI Research 研究工程师，月均 token 花费约 3000 美元；AI 已深度进入编程、检索、学习、转录等日常，但他通过个人 AI 政策、人工审查与选择性使用，抵御“AI 泥浆”和对创作与思考的侵蚀。

- 💼 背景变化：作者从大型工程团队转向研究支持与快速原型，AI 使用方式仍集中在编程、研究搜索、摘要转录与语音、写作、艺术音乐视频。
- 🧭 个人 AI 政策：他开始起草个人 AI 使用准则，希望为日常使用提供框架，并承认 AI 会渗入生活、扭曲规范，需要持续调整。
- 🤖 编程已被智能体改写：他每天管理约 5—6 个 Claude Code/OpenCode/Codex等智能体，让它们实现功能、修bug、跑测试、建PR；机器已写其90%以上代码。
- ⚡ 智能体优势：能快速原型、超快速试错、消除苦工，并让作者更敢于提出大改和代码审查建议。
- 🧑‍💻 但工程未解决：智能体独立运行会产出过度设计、难读、自嗨的“slop”，仍需人类品味、架构判断和测试验证；作者曾手写工具替换约 4000 行 vibe-code。
- 😵 使用代价：同时管理多个机器人对话令人过载疲劳，也带来编程手艺衰退的失落；代码审查转向架构、模式和智能体规则，而非逐行审查。
- 🔎 搜索与事实查询：Google AI 摘要已成默认入口，传统搜索“AI 优先”；产品搜索仍差且不可信，酒吧冷知识仍好用。
- 🎓 学习与教学：LLM 是强大老师，可逐步讲解、苏格拉底式提问、测验理解；但作者担心它太偏向“替你做”，削弱需慢思考的学习。
- 🧪 研究：文献搜索已成首选，但 LLM 仍可支持任意主张、带偏见；在新颖研究协作上表现不佳，容易让作者陷入“AI 雾”，人类专家仍更可靠。
- 🎙️ 摘要、转录与语音：摘要和转录“无聊地好用”，本地免费模型可 dictate 给电脑；语音除听写外仍未找到自然、私密、足够有用的场景。
- ✍️ 写作：仍不用 AI 从零写作或列大纲；仅让智能体写实验文档/README 并要求标明 AI 身份；AI 写作冗长空洞，编辑平庸且谄媚，但“找词”仍好用。
- 🎨 艺术、音乐与视频：图像生成整体净负面，因 AI slop 正取代人类艺术；AI 音乐在非商业、作为人类创造力透镜时有趣，商业化后令人反感；视频生成多为广告和垃圾内容。
- 🚀 结论与订阅：这一年是“勇敢新世界”的开端，AI 既产 corporate slop 也帮助人们学习和创造；他订阅 Claude Pro 与 GitHub Copilot Pro，已取消 OpenAI。

### [A2UI 1.0：构建令人愉悦、快速、可靠的智能体体验 - Google 开发者博客](https://developers.googleblog.com/a2ui-10-build-delightful-fast-reliable-agentic-experiences/)

A2UI 1.0 是 Google A2UI 团队发布的生成式 UI 开放协议首个稳定版，让 AI 智能体以可交互界面（如表单、图表、卡片）回应，而不再只输出大段文本；应用使用自身原生组件安全、低延迟地渲染，并可通过开源渲染器与智能体 SDK 接入。

- 🚀 **正式发布 1.0**：这是首个稳定版本，支持 Web、Android、iOS 渲染器及 Python、TypeScript、Dart 智能体 SDK。
- 🧩 **核心机制**：智能体描述要展示的内容，应用接收 A2UI 消息后用原生组件渲染，兼顾低延迟、高信任与原生体验。
- 🎨 **个性化与品牌一致**：UI 可按用户需求即时生成，并只使用开发者注册的设计系统和组件。
- 🛡️ **生产级能力**：支持 A2UI Express 或“系统一”决策模型选择组件；服务端绑定数据与子组件，敏感值不进入模型，并支持边生成边流式呈现。
- 🔄 **1.0 新特性**：新增双向函数调用、可访问性支持与扩展元数据；渲染器覆盖 React、Angular、Lit、Flutter、SwiftUI，Jetpack Compose 暂为 0.9.1。
- 🌐 **MCP Apps 集成**：A2UI 屏幕可出现在支持 MCP Apps 的 AI 助手中，如 Claude 和 Gemini。
- 🏢 **企业采用**：Atlassian 将 A2UI 用于 Jira 智能体交互卡片；Alation 用其渲染指标卡、图表和 SQL 透明信息；ByteDance 为 Lynx 发布渲染器；Bloomberg 等公司也在构建。
- 🧪 **应用示例**：同一智能体输出可跨手机和笔记本原生呈现，例如整合日历、餐厅订位与打车价格的晚餐安排视图；Gemini Notebook 用卡片询问并确认幻灯片选项。
- 🔮 **后续计划**：Jetpack Compose 1.0 支持即将推出，Gemini Enterprise 将升级至 1.0，路线图还包括跨平台设计系统原语和决策模型官方 SDK 支持。
- 🛠️ **上手方式**：可在 a2ui.org 阅读文档与快速开始，使用 CopilotKit 的 A2UI Playground 体验，并在 GitHub 提交问题与讨论。

### [GitHub - joshpuckett/allo：Allo 是你身边友好的字体，免费且开源 · GitHub](https://github.com/joshpuckett/allo)

Allo 是一款免费开源的友好型可变字体，专为屏幕和界面设计，支持字重、圆润度与光学尺寸调节，并提供静态字体、可变字体、Web 字体及 npm 安装方式。

- 🔤 开源字体：Allo 免费开源，采用 SIL Open Font License 1.1，可商用、修改和再分发，但不能单独售卖字体。
- 🎛️ 三个可变轴：光学尺寸 opsz 9–32（默认 14）、字重 wght 100–900（默认 400）、圆润度 ROND 0–100（默认 50）。
- 📦 字体文件：提供 18 个静态字体（Thin 到 Black，各带 Oblique）、AlloVariable.ttf，以及 WOFF2 网页字体。
- 🌐 Web 使用：可通过 npm 安装 `allo-font`，也可自托管 `fonts/webfonts` 中的 WOFF2 文件。
- ⚡ 精简版本：`AlloVariableFriendly.woff2` 将圆润度固定为 50，文件约小一半。
- 🔠 OpenType 功能：支持单层 a、消歧字形、开放数字、表格数字、分数、上下标、大写旁标点、连字和上下文替代等。
- 🖥️ 屏幕优化：光学尺寸随字号自动调整，Display 更紧凑，小字号主要调整间距。
- 🛠️ 构建方式：需 Python 3.9+，运行 `build.py` 可生成字体文件、校验和与发布压缩包，构建可复现。
- 📐 源文件结构：`Allo.designspace` 含 48 个主 master 和 8 个稀疏图层；静态字体从可变字体母版切出后单独编辑，斜体为独立绘制。
- 🤝 贡献规则：发现问题或缺字可开 issue；目前暂不接受直接修改母版或字体文件的 Pull Request。
- 🌱 来源与致谢：Allo 基于 Inter 4.2 起步，但所有字形均已重绘，并参考 Honk Sans 的温暖趣味风格。

### [Flashwright：最快的端到端测试框架，Playwright 的即插即用替代方案](https://flashwright.dev/)

Flashwright 是可直接替换 Playwright 的超快端到端测试框架，保持相同 API、测试运行器与 `npx playwright test` 命令，现有测试套件无需修改即可运行，并在基准测试中显著快于 Playwright 及其他主流工具。

- 🚀 直接替换 Playwright：导入、配置、命令行、浏览器、报告器、Trace Viewer 和 VS Code 扩展均沿用 Playwright。
- ⚡ 性能突出：24 个 TodoMVC 测试在 1 worker 下为 2.36 秒，Playwright 为 4.48 秒；4 workers 下为 1.47 秒，Playwright 为 3.02 秒。
- 🥇 对比 9 种工具仍最快：同一机器、同一 Chromium、各自推荐等待与隔离策略下，Flashwright 中位耗时最低。
- 📦 安装简单：`npm i -D @playwright/test@npm:flashwright-test`，随后继续使用 `npx playwright test`。
- 🛠️ 提速机制：复用热浏览器但重置上下文、页面变化驱动等待、输入不等待动画、提前启动 workers、V8 代码缓存、更快截图编码。
- 🤖 适合编码代理：暖会话下重跑一个 TodoMVC 测试仅 72 毫秒，Playwright 为 652 毫秒；MCP 支持自适应等待。
- ⚙️ 默认更快但可配置：`isolation: 'recycled'`、`failFastWhenIdle: true`、`waitForAnimations: false`、`testOrder: 'longest-first'` 等。
- 🔄 可恢复 Playwright 行为：可在项目、文件或 `describe` 块中逐项开启 Playwright 默认行为。
- 🌐 浏览器差异：主要提升 Chromium；Firefox 与 WebKit 基本保持 Playwright 行为，仅复用每 worker 一个标签页。
- ✅ 兼容性验证：Playwright 自有测试套件在 Chromium 上通过 2610/2610，runner、library 和 MCP 套件与 Playwright 1.64.1 一致。
- ↩️ 可随时回退：执行 `npm i -D @playwright/test@1.64.1` 即可，代码中不引用 Flashwright。

### [答案从未在明面上。先动手](https://yewjin.substack.com/p/it-was-never-obvious-start-anyway)

文章面向 AI 时代刚起步的年轻职场人：不确定性并非这一代独有，回看才会显得清晰；与其等待迷雾散去，不如从“手艺 + 需求”出发，优先学习、主动建立真实连接、为自己争取机会，并在 disruption 的裂缝中寻找自己能填补的缺口，先开始再说。

- 🌫️ 每一代人的职业起点都充满不确定性；过去看似清晰只是后见之明，迷雾不是等待的理由。
- 🛠️ 用“手艺 + 需求”替代宽泛的 ikigai：持续打磨你忍不住反复做的事，再把它指向真实问题。
- 🔁 手艺让你看见需求，需求又告诉你下一步该学什么；保持这个循环，减少对单一岗位、技术或未来预测的依赖。
- 💰 不必在意义与金钱之间二选一；多数人可以在广阔中间地带做有价值且能体面谋生的工作。
- 🧭 不要让父母、学校或职业建议行业替你决定路径；“安全选择”本身也在快速变化，要诚实面对自己能否长期坚持。
- 📚 第一份工作应优先优化学习而非薪水：靠近更强的人、接触真实问题和行业运作；起薪不是终身收入的最终预测。
- 🚪 入门级招聘收紧时，别只海投简历；用具体短讯联系真人、做 demo 展示能力、认真准备并跟进，以真实连接突破噪音。
- 👥 找到同阶段伙伴并定期见面，再连接几位前辈；这是低成本的职业加速器，也能在申请无回音时提供支持。
- 🙋 早点为自己争取、押注自己；冒名顶替感会不断移动门槛，而有趣项目和更大舞台常属于敢开口的人。
- ✨ AI 时代判断力、品味、伦理和人际连接更珍贵；disruption 的裂缝就是新需求，找到你能填补的缺口并开始。

### [五项正在改变我对软件工程中人工智能看法的研究](https://newsletter.getdx.com/p/five-studies-that-are-changing-how)

这五篇研究共同表明：AI 正在显著压缩编码等上游工作，但瓶颈已转向评审、集成、验证与理解；代码生成提速并未等比例转化为交付价值，开发者体验和团队共享理解也可能被侵蚀。

- 🧪 GitHub Copilot 观察性剂量反应研究覆盖 16,223 名开发者、43 周，发现高使用周的人均每小时完成 PR 数约高 40%，且大 PR 收益更明显，说明提升不只是把工作切小。
- 🚚 NBER 对 10 万 + GitHub 开发者的研究显示，AI 使提交量从自动补全约 +40%、交互式代理 +140% 升至自主代理 +180%，但发布量最多约 +30%；AI 与人工努力仍以互补为主，替代弹性约 0.25。
- ⚖️ 一项为期 6 个月、95 名工程师的纵向研究发现，84% 参与者持续认为生产力提升，但报告至少一个维度 DevEx 变差的比例从 14% 升至 27%，出现“生产力—体验悖论”，心流最易受损。
- 🛠️ 对 860 名微软开发者的调查提出“有界委托”：开发者希望 AI 承担文档、边缘用例测试等装配工作，但不接管核心逻辑、架构和关键决策，并强调权限范围、数据来源、不确定性提示和最小权限四类护栏。
- 🧠 Margaret-Anne Storey 提出技术债、认知债与意图债三层框架：AI 有助于减少代码层技术债，却可能加速团队“不知道”的积累和意图缺失；三者会相互放大。
- 🚧 综合结论是：瓶颈已经下移，但工具、指标和团队设计尚未跟上；未来重点在于把验证、评审、集成和共享理解当作一等交付物来建设。
