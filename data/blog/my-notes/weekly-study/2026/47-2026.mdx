### [让前端项目在人类来不及审查时更快交付的 10 个反 AI 垃圾代码举措](https://evilmartians.com/chronicles/ten-anti-ai-slop-moves-for-frontend-projects-going-faster-than-humans-can-review?ref=tailwindweekly.com)

AI 生成代码的速度已超过人类审查能力，而模型缺乏长期记忆与生产责任。文章面向 TypeScript/React 前端项目，提出 10 项“反 AI 粗制代码”检查：先用契约、类型和边界阻止问题代码产生，再用变异测试、死代码与重复代码检测发现问题，最后通过 CI 强制执行，并建议渐进式落地，避免规则一次性全开导致团队放弃。

- 🧠 **核心背景**：AI 能一周写出过去一个团队规模的代码量，但不记得昨日约定、不为生产负责，也无法在半年后解释决策；审查与理解责任仍归人类。
- 📜 **API 契约优先**：用 OpenAPI 生成类型、客户端和 Zod 校验，避免模型臆造 `user.fullName` 这类不存在的字段；前提是契约权威且后端持续维护。
- 🔒 **严格 TypeScript**：开启 `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`，迫使代码显式处理空数组、缺失字段和可选属性。
- 🧹 **把 Linter 当行为过滤器**：重点使用 sonarjs、检测多余 Effect 的规则、Vitest/Playwright 测试规则、jsx-a11y，以及禁止 `any`、非空断言、缺失返回类型等 TypeScript 规则。
- 🧱 **预设分层边界**：用 eslint-plugin-boundaries、dependency-cruiser 或 oxlint 限制依赖方向，例如组件可依赖服务、服务不可依赖组件，设计系统与业务状态隔离，mock 不进入生产构建。
- 🩹 **把重复错误变成自定义规则**：自定义规则成本已大幅降低；行为过滤器用于抵消 AI 默认习惯，“伤疤规则”用于记录真实事故，若说不出事故就不要写规则。
- 🧭 **把规则放到模型面前**：通过项目规则文件、skills 和 react-doctor 等在生成时提供约束；但预防是概率性的，不能替代后续检查，分数应作诊断而非目标。
- 🧪 **用变异测试测试测试**：Stryker 故意破坏代码，暴露只覆盖不断言、快照未验证、断言复刻实现、只检查 mock 等弱测试；不要设失败阈值或把分数当 KPI。
- 📉 **用 Knip 找死代码**：AI 更爱加代码而非删代码；Knip 可找未引用文件、导出和依赖，但要定期审查 ignore 列表，并用小型自定义脚本补充可达性、过期 `vi.mock()` 等仓库特有问题。
- 👯 **用 jscpd 找重复代码**：AI 常另写一份实现而不搜索已有 helper；jscpd 查文本重复，标记与逻辑应用不同阈值，语义重复仍需人工判断。
- 🚦 **CI 强制执行**：格式与 lint、`tsc`、单测、PR diff 上的变异测试、构建应拆成独立任务，部署依赖其通过；可跳过的检查等于没有检查。
- 💸 **承认成本**：误报、规则老化、变异测试耗时、自定义检测器维护、新人被大量规则淹没都是代价；错误信息要解释“为什么”和“该怎么改”。
- 🪜 **渐进式推广**：先在新代码/变更文件上以 warning 建立基线，再逐条把抓到真实问题的规则升级为 error，最后才加 CI 门禁，避免数千错误导致放弃。
- 🎯 **适用条件**：代码会存活超过一个季度、作者之外有人读、bug 会影响开发团队之外时更值得；若只做一件事，先上 API 契约，其次变异测试，最后 CI 门禁。
- 🧑‍⚖️ **自动化不能替代判断**：这些检查无法判断功能是否错误、抽象是否过早、状态是否该放 URL、架构与产品品味是否合理；全绿只说明未发现其设计内的问题，不证明有人理解了代码。
- 🛠️ **配套技能**：文章提供 `anti-slop-audit` 评估仓库中各项检查的收益并规划小 PR，`anti-slop-rollout` 每次执行一步，按“先警告、最后 CI 门禁”的顺序落地。

### [构建多智能体系统：3 种模式，简单解释](https://kadhar.dev/blog/multi-agent-systems-from-scratch)

本文作者以自己做的“晚餐推荐”单智能体为例，说明并非所有任务都需要多智能体；只有当任务的不同部分需要不同指令或工具、可以并行、或需要单独测试时才值得拆分。文章介绍了三种常见多智能体模式（流水线、编排者、黑板），并结合其天气助手项目 Stormwise 的评测经验，总结出坏数据传递、提示词不如正确数据、预算在难例上失效、自动检查器也会出错、循环与成本等实际问题，最后给出应当在第一天就加入的护栏建议。

- 🍽️ **先从一个智能体开始**：作者的晚餐推荐器只是“一个模型 + 三个工具（定位、天气、餐厅搜索）+ 步数上限”就完成了工作；拆成多个智能体会更慢、更贵且没有收益。
- 🔪 **何时值得拆分**：任务的各部分需要非常不同的指令或工具、各部分可以同时运行、或希望单独测试每个部分时才拆分；若一个智能体加好工具已能胜任、速度与成本更重要、或还说不清每个智能体该负责什么，就保持单智能体。
- 🏭 **模式一：流水线（Pipeline）**：像装配线，每个智能体按固定顺序完成一步并把结果交给下一个，步骤之间不回头；适合能提前写成清单的流程，最容易测试，但很僵化，一旦需要回退就容易演变成其他模式。
- 👨‍🍳 **模式二：编排者（Orchestrator）**：由主导智能体规划、分派任务并汇总结果，辅助智能体只与主导者通信、彼此不通信；Claude 和 ChatGPT 的“深度研究”功能就是这种模式，适合知道需要哪类帮助但细节取决于请求的情况，风险是主导者规划失误会让所有辅助者继承错误。
- 🧑‍🏫 **模式三：黑板（Blackboard）**：没有老板，智能体读写同一块共享白板，在有用时介入；适合事先无法确定步骤的场景（如调试），最灵活但最难测试、最容易陷入循环，因为没有人负责整体计划。
- 🧪 **实验演示**：文章提供一个脚本化演练，可用同一晚餐请求分别走三种模式，并故意“搞坏”（如让天气智能体返回过时数据、允许智能体互相回传任务），对比关闭与开启护栏时的行为。
- 🚨 **Stormwise 的教训一：坏数据会被当作事实传播**：天气服务发布的测试警报被流水线当成真实警告，模型只是合理地相信了上游；多智能体场景下这是默认风险，B 智能体分不清 A 的猜测与事实，应在每次交接处用普通代码校验数据。
- 📊 **教训二：正确数据胜过巧妙提示**：无警报访问时，助手在 69 个案例中有 26 个（38%）在警报生效期间告诉人们天气平静；加入“承认看不到官方警报”的指令反而更糟（31/69，45%）；接入真实警报并配普通提示后为零错误。
- 💰 **教训三：预算在最难的案例上失效**：适合日常问题的 token 预算在复杂案例（风暴中恰恰最重要）上会崩溃；需要预算，但应提前决定超支时的回退答案——简短安全的回答，而非半成品。
- ✅ **教训四：自动检查器本身也可能错**：作者最初的简单模式匹配脚本漏掉了 57 个真实案例中的 53 个，并指向相反结论，最终只能手工标注全部 342 条回复；若让一个智能体检查另一个，也要检查检查器。
- 🔁 **循环与成本**：循环是每个智能体都行为合理、系统却原地打转；成本更隐蔽——作者的晚餐智能体从第一天就有步数限制、从未失控，仍因 API 账单超出副业承受范围而下线；智能体越多，调用次数越多。
- 🛡️ **第一天就该加的护栏（普通代码，位于智能体之外）**：检查每次交接（格式、新鲜度、合理性）；限制跳转次数，反复弹跳后停下来问人；每个请求一个统一预算并预设回退答案；记录智能体间每条消息以便逐步回放；用真实案例测试并人工抽检自动评分。
- 🧭 **一句话总结**：先从单智能体开始，只在某部分明确需要独立指令、工具或速度时拆分，然后把大部分精力放在枯燥的部分——交接检查、限制与真实评估，因为作者的系统正是败在这些地方。

### [在删除你的 AGENTS.md 之前，请先阅读这篇文章——作者：Jina Yoon](https://newsletter.posthog.com/p/your-agentsmd-is-holding-you-back)

文章指出，上下文工程正从“不断补充信息”转向“主动做减法”，避免过多规则和提示反而拖累 AI 智能体。作者建议定期删除或重写 AGENTS.md / CLAUDE.md，并通过人工审查、评估测试和智能体反馈三种方式，让上下文保持精简、准确和可维护。

- 🧠 模型能力提升后，过去必需的上下文可能变成负担；Anthropic 曾移除 Claude Code 系统提示的 80%，Claude Code 创作者也建议每六个月删除 CLAUDE.md 以保持前沿。
- 🩺 先运行 `/doctor` 做基础健康检查：删除冗余提示、发现损坏配置、清理未使用插件、优化懒加载，并估算可节省的 token。
- 👀 `/doctor` 不能判断内容是否正确，仍需人工逐行检查 AGENTS.md；如果说不清某条规则能防止什么失败，就删除它。
- ⚠️ 文章举例：团队暂停 merge queue 后忘记更新 AGENTS.md，导致智能体在 21 小时内给出错误合并指令，说明上下文必须随外部状态同步维护。
- 🧪 把上下文当作代码来测试：每次智能体出错，就记录触发错误的提示到 `failures.md`，修改 AGENTS.md 后重跑这些提示作为回归测试。
- 🔁 PostHog 用约 40 个示例应用运行 Wizard，再由 `pr-evaluator` 评估生成的 PR，从中发现如“跳过安装 PostHog”等问题。
- 💬 直接让智能体反馈上下文缺口：在提示中询问哪些信息本可避免工具失败、错误编辑和无效轮次，并将反馈聚类、验证后用于改进上下文系统。

### [我如何使用 AI（2026 年 10 月）——本·斯托洛维茨](https://ben.stolovitz.com/posts/how-use-ai-oct-2026/)

作者在 2026 年 10 月回顾过去一年使用 AI 的变化：他从微软 Windows AI 团队工程师转为 Salesforce AI Research 研究工程师，月均 token 花费约 3000 美元；AI 已深度进入编程、检索、学习、转录等日常，但他通过个人 AI 政策、人工审查与选择性使用，抵御“AI 泥浆”和对创作与思考的侵蚀。

- 💼 背景变化：作者从大型工程团队转向研究支持与快速原型，AI 使用方式仍集中在编程、研究搜索、摘要转录与语音、写作、艺术音乐视频。
- 🧭 个人 AI 政策：他开始起草个人 AI 使用准则，希望为日常使用提供框架，并承认 AI 会渗入生活、扭曲规范，需要持续调整。
- 🤖 编程已被智能体改写：他每天管理约 5—6 个 Claude Code/OpenCode/Codex等智能体，让它们实现功能、修bug、跑测试、建PR；机器已写其90%以上代码。
- ⚡ 智能体优势：能快速原型、超快速试错、消除苦工，并让作者更敢于提出大改和代码审查建议。
- 🧑‍💻 但工程未解决：智能体独立运行会产出过度设计、难读、自嗨的“slop”，仍需人类品味、架构判断和测试验证；作者曾手写工具替换约 4000 行 vibe-code。
- 😵 使用代价：同时管理多个机器人对话令人过载疲劳，也带来编程手艺衰退的失落；代码审查转向架构、模式和智能体规则，而非逐行审查。
- 🔎 搜索与事实查询：Google AI 摘要已成默认入口，传统搜索“AI 优先”；产品搜索仍差且不可信，酒吧冷知识仍好用。
- 🎓 学习与教学：LLM 是强大老师，可逐步讲解、苏格拉底式提问、测验理解；但作者担心它太偏向“替你做”，削弱需慢思考的学习。
- 🧪 研究：文献搜索已成首选，但 LLM 仍可支持任意主张、带偏见；在新颖研究协作上表现不佳，容易让作者陷入“AI 雾”，人类专家仍更可靠。
- 🎙️ 摘要、转录与语音：摘要和转录“无聊地好用”，本地免费模型可 dictate 给电脑；语音除听写外仍未找到自然、私密、足够有用的场景。
- ✍️ 写作：仍不用 AI 从零写作或列大纲；仅让智能体写实验文档/README 并要求标明 AI 身份；AI 写作冗长空洞，编辑平庸且谄媚，但“找词”仍好用。
- 🎨 艺术、音乐与视频：图像生成整体净负面，因 AI slop 正取代人类艺术；AI 音乐在非商业、作为人类创造力透镜时有趣，商业化后令人反感；视频生成多为广告和垃圾内容。
- 🚀 结论与订阅：这一年是“勇敢新世界”的开端，AI 既产 corporate slop 也帮助人们学习和创造；他订阅 Claude Pro 与 GitHub Copilot Pro，已取消 OpenAI。

### [creator-generalist：让 AI agent 具备 2D、3D 与游戏通才技能](https://github.com/codepawl/creator-generalist)

这是一个面向 AI 编程 agent 的技能包（skill pack）说明文档：一次性安装后，agent 可以像 2D/3D 通才和小型游戏工作室一样产出内容、视频与短视频；它按五大插件组织技能，并通过统一的八步制作流程、预览确认和自动 QA 检查来控制产出质量。

- 🧩 **一键扩展能力**：安装一次后，agent 可承担 2D 与 3D 通才以及小型游戏工作室的工作，用于制作 YouTube、TikTok、Facebook、Instagram 和 X 的内容、视频与 Shorts。
- 🗣️ **调用方式**：不需要直接指定技能名称；只要描述任务，匹配的技能就会自动加载，也可以用 `/3dg`、`/2dg`、`/gameg` 手动启动。
- ❓ **先澄清再动手**：构建前 agent 会就需求中未明确的部分（目的、平台、格式、外观）提几个简短问题，每问都附带建议答案，然后先给出低成本的预览，以确保结果符合意图。
- 🎬 **三大主技能**：`3d-generalist`（基于 Blender/Three.js/Crucible 的脚本化动画 3D 作品）、`2d-generalist`（采用 Vox/Johnny Harris 风格的解说图形）、`game-generalist`（可玩灰盒原型、锁定美术风格、原创游戏与机器人试玩报告）。
- 🏗️ **扩展 3D 技能**：`visualize-in-3d`（three.js 实时应用/影片/课程）、`make-pixel-splats`（高斯泼溅像素立体场景）、`build-house-from-plan`（户型图转 Blender Cycles 房屋）、`build-minecraft-model-from-image`（照片转 Minecraft 风格模型并导出 GLB）。
- 🎨 **工艺技能**：`model-characters`、`sculpt-models`、`animate-characters`、`rig-characters`、`draw-and-paint-art`、`paint-stylized-backgrounds`、`paint-with-code`，覆盖建模、雕刻、动画、绑定、绘画与代码作画。
- 🛠️ **工具技能**：`use-3d-software`（约 250 条 Blender 5.x 配方，以及 three.js、Godot、Unity、Unreal 指南与 GLB/FBX 导出规则）、`edit-video`（Resolve、CapCut、Premiere、Kdenlive、Shotcut、FFmpeg 的剪辑工艺与平台导出）。
- 👀 **学习技能**：`watch-video` 能拆解视频的帧表、剪辑、频谱与多语字幕，生成复刻配方，并支持“频道转技能”流水线，还可把 OCR 框和带时间戳的结论画回视频上供核对。
- 🔊 **声音技能**：`design-sound` 支持语义检索（CLAP）音效库、网络与 ElevenLabs 取音、用 HunyuanVideo-Foley 从默片生成拟音、按事件表铺设音效轨、按剪辑配乐，并按平台响度做混音检查。
- 📦 **插件归属**：`3d-generalist` 插件含建模、雕刻、软件使用、动画、绑定、3D 可视化等 9 项技能；`2d-generalist` 含 `edit-video`、绘画与背景类技能；`watch-video`、`design-sound`、`game-generalist` 为独立插件。全部安装五个插件即可获得所有技能。
- 🧱 **可单独安装**：`2d-generalist` 自带制作流程（production spine）与 `compare_look.py` 副本，因此 3D、2D 两个插件各自单独安装也能工作。
- ⚙️ **安装方式**：把 INSTALL.md 交给 agent 执行，它会检查 Blender、FFmpeg、Node.js、Python，并在安装程序前征求同意；也支持 Claude Code 插件市场命令、shell 命令、`npx skills add`，或手动复制技能文件夹到 `~/.claude/skills/` 等目录。
- 🎞️ **八步制作流程**：brief → reference → 脚本与节拍 → 准备与 look gate → 资产 → 构建与动画 → 声音 → QA（预览与终版）；构建前给出 A/B/C 风格帧供选择，提供首个完成镜头的 WIP 演示与 540p 预览，未经批准不会进行全质量渲染。
- 🧭 **3D 五种模式**：`cutaway`（60 秒透视剖面短片，经 5–7 轮“但…→所以…”推进）、`story`（角色驱动的滑稽短片）、`world`（单一地点与年代的环境/立体模型）、`character`（带重定向动画与双脚贴地的绑定角色）、`asset`（主角模型、道具或 PBR 材质，导出 GLB 附 CREDITS.md）。

### [五项正在改变我对软件工程中人工智能看法的研究](https://newsletter.getdx.com/p/five-studies-that-are-changing-how)

这五篇研究共同表明：AI 正在显著压缩编码等上游工作，但瓶颈已转向评审、集成、验证与理解；代码生成提速并未等比例转化为交付价值，开发者体验和团队共享理解也可能被侵蚀。

- 🧪 GitHub Copilot 观察性剂量反应研究覆盖 16,223 名开发者、43 周，发现高使用周的人均每小时完成 PR 数约高 40%，且大 PR 收益更明显，说明提升不只是把工作切小。
- 🚚 NBER 对 10 万 + GitHub 开发者的研究显示，AI 使提交量从自动补全约 +40%、交互式代理 +140% 升至自主代理 +180%，但发布量最多约 +30%；AI 与人工努力仍以互补为主，替代弹性约 0.25。
- ⚖️ 一项为期 6 个月、95 名工程师的纵向研究发现，84% 参与者持续认为生产力提升，但报告至少一个维度 DevEx 变差的比例从 14% 升至 27%，出现“生产力—体验悖论”，心流最易受损。
- 🛠️ 对 860 名微软开发者的调查提出“有界委托”：开发者希望 AI 承担文档、边缘用例测试等装配工作，但不接管核心逻辑、架构和关键决策，并强调权限范围、数据来源、不确定性提示和最小权限四类护栏。
- 🧠 Margaret-Anne Storey 提出技术债、认知债与意图债三层框架：AI 有助于减少代码层技术债，却可能加速团队“不知道”的积累和意图缺失；三者会相互放大。
- 🚧 综合结论是：瓶颈已经下移，但工具、指标和团队设计尚未跟上；未来重点在于把验证、评审、集成和共享理解当作一等交付物来建设。
