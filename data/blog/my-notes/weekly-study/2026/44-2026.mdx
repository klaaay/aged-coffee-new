## 技术

### [设计系统应默认保持快速 | Den Odell](https://denodell.com/blog/design-systems-should-be-fast-by-default)

设计系统是应用性能的基础层；若组件在真实数据量下响应缓慢，所有使用它的应用都会受影响。作者像重视可访问性一样重视性能，实测 10 个流行开源设计系统，分析慢因并提出测试、性能预算与“默认快”的改进方案。

- 🧱 设计系统位于浏览器、框架和应用代码之间，组件在主线程上的开销会直接挤占应用性能。
- ⏱️ 作者用生产构建、Chrome、4 倍 CPU 节流测试两个高频重任务：打开含 249 个国家的下拉框、一次勾选 100 个复选框。
- 📊 结果差异明显：Fluent、Carbon 打开国家选择器最快；Ionic 最慢，约 1266ms，且最长无响应约 1133ms；Ant Design 勾选 100 个复选框最慢，约 421ms。
- 🧩 性能不由框架单独决定：同用 Lit 的组件表现差异很大，同一设计系统也可能一个任务慢、另一个任务较快。
- 🔍 Ionic 慢因是 Stencil 在非 Shadow DOM 的 radio group 中处理 slot，新增选项时反复检查已有子项，呈 O(n²) 增长；可通过改用 Shadow DOM 或优化 Stencil 检查逻辑修复。
- 🪟 Material UI 国家选择器一次性渲染约 250 个元素；Ant Design 采用虚拟化，只渲染可见选项，因此明显更快，但需兼顾键盘导航和屏幕阅读器。
- 🎨 UI5 在隐藏 popover 中预置全部选项及内部 Shadow DOM，打开时一次性计算约 1500 个元素样式；React Spectrum/React Aria 存在逐个读写布局导致的 layout thrashing。
- ✨ Ant Design 复选框慢因是 100 个动画同时执行样式计算与绘制；建议仅在用户直接选择时动画，或“全选”时关闭动画，并用 opacity 合成层动画替代高成本重绘。
- 🧪 作者提供 Playwright 性能测试仓库，使用 TaskDuration 与 Long Animation Frames API，设置性能预算：总耗时低于 300ms、最长阻塞低于 100ms、选项翻倍耗时增长低于 2.5 倍。
- 🚀 建议设计系统团队把性能测试纳入每次 PR，默认提供快行为，在文档标注组件测试过的数据量上限，收集真实页面性能剖面，并在发布说明中公布性能前后指标。

### [软件慢是因为设计糟糕，而不是语言慢](https://www.seangoedecke.com/software-is-slow-because-of-bad-design-not-slow-languages/)

文章核心观点是：软件性能通常由设计决定，而非编程语言速度。大多数真实程序受 I/O 限制，重写成 C、Rust 或汇编只能优化局部 CPU 热点，难以带来数量级提升；更有效的做法是通过剖析与重新设计减少工作、缓存、异步、并行和优化查询。AI 应帮助发现热点并提出重构方案，而不是盲目重写语言。

- 🧠 软件慢往往源于糟糕设计，而不是使用了“慢语言”；语言速度并非性能主导因素。
- ⏳ 多数真实程序是 I/O-bound，时间主要花在数据库、第三方 API、磁盘和网络等待上。
- 📉 重写成 C/Rust 只能加速非 I/O 部分，受 Amdahl 定律限制，整体收益通常有限。
- 📚 慢语言常已通过 C 扩展和成熟库委托高性能工作，如 Python 的机器学习库、Markdown 渲染库。
- 🔍 真正有效的提速通常来自重新设计：缓存、异步/后台任务、并行、合并 SQL、消除 N+1、跳过不必要操作。
- 🎯 只有少数真正 CPU-bound 且无法减少工作的热点，才适合用更快语言重写局部代码。
- 🤖 使用 AI 优化软件时，应让代理做性能剖析、定位热点、建议重构，而非一开始就要求用 C/Rust/汇编重写。
- 💬 评论区争议包括 CRUD 是否真为 I/O-bound、CPU-bound 程序占比、语言生态对设计难易度的影响；作者仍坚持设计优先。
- 🧩 换语言对可移植性、效率、可维护性有价值，但若目标是原始速度，应优先优化程序设计与工作方式。

### [抱歉，但你还是得思考 | 一切都关乎比特](https://itsallaboutthebit.com/i-am-sorry-but-you-still-have-to-think/)

文章以 DHH 用 AI 代理把 Campfire 从 Rails 改写为 Rust（后又改写为 Elixir、Go）为例，讨论“不读代码、依赖 AI 编程”的局限：提示含糊会让模型隐含决定关键取舍，不同改写结果因而不可直接比较；性能基准常只测单一指标，真实系统必须在兼容性、延迟、吞吐、内存和失败模式之间权衡。结论是编程并未被“解决”，开发者仍需理解代码、系统约束与权衡。

- 🤖 DHH 让 AI 代理将 Campfire 改写为 Rust，并扩展到 Elixir、Go；作者借此观察“不读代码”的 AI 编程结果。
- ⚖️ 提示不够具体时，许多设计问题没有唯一答案，模型会替开发者隐含决定向后兼容、延迟/吞吐、内存上限、通知丢失等取舍。
- 🧩 Rust 版为缓存方便放弃 CSRF token、用进程内队列替代 Redis；Elixir 版更接近 Rails 原作；约束不同使语言间性能比较失真。
- 🧵 代码层也有问题：Elixir 版用单进程串行处理 SQL 查询；Rust 版部分数据库操作非 async、使用同步锁，在协作式调度下会阻塞 worker。
- 📊 基准测试本身也不可靠：Zach Daniels 发现 Rust 版重载下新消息通知投递成功率仅约 1%，只测吞吐会掩盖其他系统属性。
- 🔁 闭环基准测“单位时间能处理多少请求”，但真实高负载常来自大量用户同时操作，恒定的请求到达率更能模拟这类场景。
- 🧪 以 100 POST/s 重跑：Rust 事件送达约 14% 且无 HTTP 错误；Elixir 约 60%，但约 23% HTTP 请求超时，最差事件延迟接近 180 秒。
- 📉 Rust 大量丢消息的根因是 `tokio::sync::broadcast` 容量仅 256，接收端落后会触发 `Lagged`；调到 16384 后送达率升至约 90%，但延迟从 11 秒升到 130 秒以上，未必更好。
- 🧠 Elixir 的 GenServer 邮箱默认无界，压力测试中内存达 1.8GB；不设边界可能遇到外部限制，需在丢消息与 OOM 之间权衡。
- ✅ 最终结论：仍要批判性思考、理解自己在做什么，不要用单一指标判断语言优劣；可靠系统需要明确失败模式与取舍，而基准测试很难。

### [用 `small-change` 加速代码审查 | 非理性繁荣](https://lethain.com/small-changes/)

文章介绍了 Imprint 在 PR 合并量大幅提升、质量改善的同时，代码评审时长从 33 分钟升至 77 分钟并成为瓶颈；团队因此推出 `small-change` 机制，通过 CICD 检查、AI 评审和作者经验等条件筛选低风险小改动，用自动化技能快速批准，并把由此引发的错误视为系统级问题。文章还讨论了“meat proxy review”反模式和集中式 harness `fleet`，早期约 10% 变更符合 `small-change`，最终成败取决于验证能力的持续扩展。

- 📈 工程效率显著提升：Imprint 平均工程师的 PR 合并量是两年前的 4 倍，两个团队达到 10 倍，个别工程师达到 25 倍。
- ✅ 质量同步改善：事故半年环比下降 42%，严重事故下降 78%，说明质量与速度并非简单取舍。
- ⏱️ 评审成为瓶颈：PR 评审中位数从两年前的 33 分钟增至 77 分钟，且与合并 PR 数量高度相关。
- 🧭 重新审视评审目的：知识共享、防错、防恶意行为和合规；现代开发范式下，部分目标可用更好机制替代逐 PR 人工评审。
- 🧩 `small-change` 资格标准：少于 1000 行代码、AI 评审无 p1/p2 问题、作者在相关服务有 10+ 合并经验、影响服务数少于 N（前端为 1，后端为 3），共享库和工具文件不适用。
- ⚙️ 执行机制：CICD 生成 GitHub check 决定资格，标签仅用于可见性；Slack reacji 标识状态；仓库内 `.small_change` 支持按路径定制。
- 🤖 自动化技能：`review-small-change` 只批准或忽略、不发表评论，避免“meat proxy review”；`review-pr-cluster` 批量识别共性问题。初版约两天完成上线，后续长期调参。
- 🧠 文化原则：任何由 `small-change` 引发的错误都应在系统层解决，改进 AI 评审、验证机制、CICD 和 harness。
- 🚫 “meat proxy review”反模式：让 harness 生成大量评论、再用 harness 回复，形成没有学习价值的评审幻觉；应投资集中评审机制并直接批准。
- ☁️ `fleet`：集中编排的云端 harness，用独立评估决定所需评审人数，安全变更可仅需 1 人评审。
- 📊 早期结果：约 10% 变更符合 `small-change`，可获得快速批准，除非涉及安全或资金等敏感主题；未来需扩大比例并增强验证。
- 💬 接受度：变革让部分人不适，需要持续重新评估长期最佳实践是否已变成教条。

### [OxideTerm](https://github.com/AnalyseDeCircuit/oxideterm)

该工具是一个用 Rust + GPUI 编写的、面向本地 shell 与远程机器的 AI 原生工作区，强调零 WebView、零 OpenSSL、零遥测且无需应用订阅。终端、SFTP、端口转发、编辑器、监控与 AI 都围绕同一台服务器节点组织，UI 与 SSH 后端运行在同一个 Rust 进程中。

- 🚀 **快速上手**：安装后，可在 Session Manager 中新建 SSH 连接，或从 `~/.ssh/config` 导入主机；打开终端时，会用 `~/.ssh/known_hosts` 校验主机密钥；SFTP、端口转发和内置编辑器默认共用同一条 SSH 连接；AI 功能需在设置中自行配置服务商端点来启用。
- 🖥️ **终端与协议**：支持本地 shell、SSH、Mosh、Telnet、Serial、分屏窗格、多跳路由、SSH agent 及转发、2FA/TOTP、X11 转发、命令标记、会话日志与录制、Sixel/Kitty 图形、trzsz 传输。
- 🪟 **tmux 与广播**：提供原生 tmux `-CC` 控制模式（窗格布局、可拖拽分隔条）、命名广播组，以及可按计划重复输入的多目标命令发送器。
- 🔁 **连接可靠性**：Grace Period 重连会先探测旧连接 30 秒再替换，从而让 TUI 程序挺过短暂断网，并恢复转发、传输和已打开的编辑器文件；重连后，旧连接的 SFTP 会话不会被静默迁移到新连接。
- 📁 **文件与编辑**：SFTP 双栏管理器、带限速与预计剩余时间的传输队列、书签、支持安全写入与冲突处理的内置远程编辑器，以及工作区恢复。
- 🌐 **网络能力**：本地、远程和动态 SOCKS5 转发，规则保存，远程端口检测，连接拓扑查看，临时 socket 调试。
- 🖥️ **远程桌面**：可从插件市场安装 RDP 或 VNC，并使用原生查看器，支持剪贴板和输入。
- 📊 **主机运维监控**：可查看进程、服务、日志、端口、任务、磁盘、软件包、容器和 tmux。
- 🤖 **OxideSens AI**：自带密钥（BYOK），支持 OpenAI、Anthropic、Gemini、Ollama 及 OpenAI 兼容端点；支持 MCP（stdio/SSE）、本地 RAG（BM25 + 向量索引）、Agent Skills；工作区上下文与动作需用户批准，命令策略规则生效，发送前做凭据模式脱敏，密钥存于系统钥匙串。
- 🧩 **三类插件**：仅清单（无代码）、WASM（Wasmtime/WASI 或 sidecar，能力受限）、普通本地进程（受信任代码，不经 OS 沙箱）；旧版 Tauri 1.x ESM 插件可被列出但不会被原生 2.x 执行。
- 🔒 **安全与隐私**：凭据存储于 macOS Keychain / Windows Credential Manager / libsecret；敏感类型使用 zeroize；主机密钥采用 TOFU 并拒绝意外变更；`.oxide` 导出使用 ChaCha20-Poly1305 + Argon2id（256 MB、4 次迭代）；会话录制与审计默认关闭且加密留在本机，录制不捕获键盘输入；无遥测。
- 🛡️ **CLI 安全护栏**：会改变状态的命令提供 dry-run 计划、`--yes` 确认与回滚备份。
- 📉 **内存占用**：从 Tauri 1.x 迁移到原生 GPUI 2.0 后，维护者记录的 macOS 空闲内存由 318.7 MB 降至 81.3 MB（约 74%），Windows 由 182.4 MB 降至 23.5 MB（约 87%）；旧版本数据包含相关 WebView 进程。
- 🧱 **架构与技术栈**：GPUI 在 GPU 上直接渲染，终端字节直接更新 `TerminalState`，无 JSON/WebSocket/Base64/xterm.js 解析环节；`NodeRouter` + `SshConnectionRegistry`（DashMap）实现按节点连接池；SSH 使用 russh + ring（无 OpenSSL/libssh2）；另有 portable-pty、alacritty_terminal、tree-sitter、Tokio、Wasmtime 等。
- 💻 **无头 CLI**：`oxideterm` CLI 不启动桌面应用即可用于自动化、CI 与诊断，覆盖设置、连接、转发、插件、密钥、便携包、报告、批量计划、备份、云同步，支持 `--json`/`--dry-run` 与配置目录隔离。
- 📦 **安装与限制**：提供 macOS DMG、Windows 安装程序、Linux AppImage/.deb/.rpm（x64 与 ARM64），可用 `sha256sums.txt` 校验；仅桌面端（无移动应用），项目迭代频繁，进程插件无 OS 沙箱；渲染异常时可设 `OXIDETERM_RENDER_PROFILE=compatibility`；许可证为 GPL-3.0-only。

### [Tinyauth](https://github.com/tinyauthapp/tinyauth)

Tinyauth 是一个极简的 OpenID Certified™ 认证与授权服务器，可作为应用认证中间件或独立认证服务器，支持 OAuth、LDAP、访问控制及主流反向代理；项目处于活跃开发期，目前由单人维护，并呼吁社区开发者协助。

- 🧩 定位：号称“史上最小”的认证与授权服务器，兼顾中间件和独立服务两种使用方式。
- 🔐 能力：支持 OAuth、LDAP、访问控制，并兼容 Traefik、Nginx、Caddy 等流行代理。
- ⚠️ 开发状态：项目活跃开发中，配置可能频繁变化，升级前应仔细阅读发布说明。

- 🛠️ 维护现状：截至 30/10/2026，项目由单人维护；AI 代理持续提交大量缺陷和安全报告，其中部分有效、部分无效，审查与修复耗时较多。
- 🤝 寻求协助：开发者可通过 Discord 或 hello@tinyauth.app 联系维护者并提供帮助。

- 📚 社区资源：提供文档、Discord 服务器、贡献指南和 Crowdin 本地化页面。

### [TBM 447：我们为何自毁职业生涯——作者：约翰·卡特勒](https://cutlefish.substack.com/p/tbm-447-why-we-sabotage-our-careers)

文章认为，职场中的“自我破坏”往往不是单纯的个人缺陷，而是对有害环境、价值受威胁、脆弱情绪和身份困境的保护性反应。作者提醒，更强的自我监控与“修复自己”可能复制问题；更可行的方向是承认真实伤害与需求、允许感受、接受局限，同时保留选择与行动空间，学会与内在不同部分共舞。

- 🛡️ 自我破坏可能是保护机制：即时后果虽有害，却在帮人回避更痛苦的感受或威胁。
- ⚠️ 反应可能源于真实问题：有毒行为、失能环境或不公处境，不能被简单归因于个人认知扭曲。
- 💎 保护价值也可能把价值推远：为避免脆弱、不确定和责任，人可能不敢真正追求在意之事。
- 🧠 过度思考是情绪防御：分析能带来控制感，但不能替代真实的情感体验。
- 🌬️ 允许自己感受很有力量：不立刻反应或改变，不等于投降，而是为下一步选择腾出自由。
- 🔁 过度自我修正会强化旧模式：持续自我监视、压制和纠正，可能复制原本造成问题的压力。
- 🎭 自我怀疑与强硬防御同源：长期被否定后，人可能压抑需求，也可能激烈反击并损害关系与机会。
- 🪞 想改变他人也是一种保护：接受影响力有限会带来悲伤，但不必因此放弃价值或容忍伤害。
- 🏷️ 给人贴标签也在给自己派角色：把他人视为傲慢领导或无知同事，可能把自己锁进“真相讲述者/局外人/修复者”的叙事。
- 🏢 职场环境特殊且矛盾：权力、评估与自我监控交织，而过度自信、支配性等触发防御的特质有时反被奖励。
- ❤️ 不是所有情绪都需调节：对归属、支持与尊重的失望可能是真实丧失，而非情绪管理失败。
- 🗣️ 抱怨和失望是正常的：不必把每次挫败都转化为成长课题或解决方案。
- ⚔️ 可以有真实对手：愤怒和抵抗可以正当，但别让斗争占据身份与内心平和。
- 🪤 持续自我提升会成陷阱：把觉察和疗愈变成新标准，会让人更擅长找自己的问题。
- 🌗 承诺常同时来自爱与伤：不要因有伤痛就否定信念，也不要因热情真诚就忽略底层创伤。
- 🧭 威胁反应不都是误报：目标不是消除张力，而是更能与矛盾需求共处。
- ✅ 接纳不等于不改变：可行动、关心并推动改变，同时接受无法控制结果。
- 🚪 否认能动性也是保护：承认控制有限，不等于否认仍有的选择。
- 🔍 解释既解放又限制：理解原因能带来接纳，也可能变成困住自己的标签。
- 💼 工作与职场不是一回事：不必把每次职场冲突都上升为价值、能力或身份的公投。
- 🌱 人与工作的关系会变化：成长有时不是做得更好，而是改变什么重要、能容忍什么、不再需要证明什么。
- 💃 最终不是修好自己，而是与自己共舞：接纳不同内在部分，让它们争斗、支持并共存，而不是让某一部分获胜。

### [我现在面试时会问的九个问题，真希望五年前就问过](https://louisedeason.substack.com/p/nine-questions-i-now-ask-in-interviews)

- 🗣️ 分歧处理：问团队如何应对领导层决策分歧；健康团队有表达和反馈流程，而非一味“相信领导”。
- 👥 招聘计划：问未来 12 个月编制计划；不确定或未获批可能意味着团队未来仍在高层博弈。
- 🤝 未来同事：问最常合作的人是谁，并请求在流程中与其交流；安排是否顺畅本身就是信号。
- 🎯 成败定义：问六个月成功与失败分别是什么样；失败答案常暴露岗位的真实模糊性、政治性或倦怠风险。
- 🔄 重组历史：问最近一次重组时间与触发原因；频率和原因反映组织稳定性。
- ❓ 岗位空缺原因：直接问“为什么这个职位开放”；区分增长、补缺、重组，并注意回答是否迟疑。
- 🚪 反向筛选：若公司因这些问题不悦、敷衍或让你觉得自己“难搞”，说明它不愿被面试，应果断放弃。
